## 1. 背景与目标

### 1.1 背景

播客笔记助手已经过多轮 prompt 迭代（v1.6.x ~ v1.7.x），解决了内容遗漏、wiki-link 缺失、实体分类错误等核心问题。当前 prompt 体系包含三层质量保障：转录校对（CORRECTION_PROMPT）、笔记生成（AI_PROMPT，temperature 0.3，max_tokens 16384）、程序化后处理（缺失卡片补全、人物过滤）。

但用户仍反馈部分播客笔记不完整（如「生活需要平替」「Agent动力学」两期），根因是长播客（转写文本 > 30000 字符）一次性输入 AI，输出 token 上限（16384）截断导致后半部分内容丢失。此外，缺乏系统化的质量评估机制，问题发现依赖用户反馈，响应滞后。

### 1.2 目标

在现有 prompt 基础上，通过长文本分段处理和质量评估机制，将笔记完整度从"依赖 token 上限"提升为"可度量、可保障"。

### 1.3 质量维度

| 维度 | 当前状态 | 目标 |
|------|---------|------|
| 笔记完整度 | 短播客好，长播客截断 | 任意长度播客均完整覆盖 |
| 实体分类准确率 | 程序化兜底（人物过滤+缺失补全） | AI 端一次生成准确率 > 95% |
| wiki-link 覆盖率 | prompt 强制要求，偶有遗漏 | 正文首次提及 100% 覆盖 |
| 质量可观测性 | 无，依赖用户反馈 | 每次处理输出质量评分 |

## 2. 需求概述

三个功能模块：长文本分段处理（解决截断问题）、质量评估与评分（发现问题）、prompt 持续优化机制（预防问题）。

## 3. 功能详细设计

### 3.1 长文本分段处理（US-001）

**功能描述**：当转写文本超过阈值时，将文本分段输入 AI，各段独立生成笔记片段，最后合并为完整笔记。

**优先级**：P0

**业务规则**：
1. 分段阈值：转写文本 > 30000 字符时触发分段（约 60 分钟播客）
2. 分段策略：按自然段落边界切分，每段 20000-25000 字符，段间重叠 500 字符保证上下文连续
3. 分段数量：最多 3 段（覆盖约 2.5 小时播客），超过 3 段时取前 3 段并日志告警
4. 第一段 prompt：包含完整的 AI_PROMPT 模板 + 分段说明（"这是播客转写的第 1/N 段，请仅针对本段内容生成笔记"）
5. 后续段 prompt：仅要求补充本段新增的内容要点、实体和术语，不重复已生成的部分
6. 合并策略：第一段输出作为基础，后续段的新增内容追加到对应模块（内容概览追加要点、实体索引追加条目、术语词典追加词条、CARD 块追加卡片）
7. 合并后去重：对实体名称和术语名称去重，保留首次出现的完整描述
8. 短播客不受影响：< 30000 字符的播客走原有单次处理流程，零性能开销

**交互流程**：
1. 用户触发播客处理（单文件或批量）
2. Step 4（修正专有名词）：对完整转写文本分段校对后拼接（校对 prompt 短，不需要分段）
3. Step 5（AI 提炼笔记）：检测文本长度，> 30000 字符则进入分段模式
4. 分段模式下，进度条显示"AI 提炼笔记 (1/3)"、"(2/3)"、"(3/3)"
5. 各段结果合并后输出最终笔记

**异常处理**：

| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 某段 AI 调用失败 | 重试该段（复用现有重试机制），3 次失败后跳过该段 | 进度显示"第 N 段生成失败" |
| 合并后笔记格式异常 | 回退到仅第一段结果 | 日志记录，不影响用户 |
| 文本恰好 30000 字符 | 走单次处理（不触发分段） | 无提示 |

### 3.2 质量评估与评分（US-002）

**功能描述**：每次 AI 笔记生成后，程序化评估输出质量，生成评分并记录到日志，为后续 prompt 优化提供数据支撑。

**优先级**：P1

**业务规则**：
1. 评估时机：笔记合并完成后、写入文件前
2. 评估维度与权重：

| 维度 | 权重 | 评估方法 |
|------|------|---------|
| 内容覆盖率 | 40% | 转写文本中的关键名词在笔记正文中出现的比例 |
| 实体完整度 | 25% | CARD 块数量 / 正文中 `[[wiki-link]]` 去重数量 |
| wiki-link 覆盖 | 20% | 正文中首次提及的人名/项目名被 `[[ ]]` 包裹的比例 |
| 格式合规性 | 15% | frontmatter 完整性 + 必要模块（A、G）是否存在 |

3. 评分输出：0-100 分的综合评分 + 各维度分项得分
4. 评分记录：写入处理日志（已有 step callback），显示在任务完成通知中
5. 评分阈值：< 60 分时日志标红告警，提示"笔记质量偏低，建议人工复核"
6. 评分不影响流程：无论评分高低，笔记正常写入，评分仅作为参考

**交互流程**：
1. 笔记生成完成后，程序自动评估
2. 任务面板显示：`✓ AI 提炼笔记（质量评分: 82/100）`
3. 评分 < 60 时显示：`⚠ AI 提炼笔记（质量评分: 45/100，建议复核）`
4. 评分详情记录到日志，可通过日志文件查看

### 3.3 Prompt 模板可配置（US-003）

**功能描述**：将 AI_PROMPT 和 CORRECTION_PROMPT 从硬编码改为外部文件加载，方便迭代调试而无需重新构建应用。

**优先级**：P2

**业务规则**：
1. 模板文件位置：`{userData}/prompts/note-generation.md` 和 `{userData}/prompts/transcript-correction.md`
2. 加载优先级：外部文件 > 内置硬编码（fallback）
3. 热加载：修改外部模板文件后，下次处理自动生效，无需重启应用
4. 模板格式：纯文本 Markdown，保留 `{date}`、`{transcript}` 占位符
5. 内置模板导出：首次启动时将内置模板写入 `{userData}/prompts/` 作为参考模板
6. 模板验证：加载后检查必要占位符是否存在，缺失则回退到内置模板并告警

## 4. 数据模型

### 4.1 QualityScore 接口

```typescript
interface QualityScore {
  overall: number          // 0-100 综合评分
  contentCoverage: number  // 内容覆盖率 (0-100)
  entityCompleteness: number // 实体完整度 (0-100)
  wikiLinkCoverage: number  // wiki-link 覆盖 (0-100)
  formatCompliance: number  // 格式合规性 (0-100)
  details: string          // 评估详情（如"缺少 3 个实体卡片"）
}
```

### 4.2 StepCallback 扩展

现有 step callback 的 `detail` 字段已支持自由文本。质量评分通过 detail 字段传递，无需新增 IPC 通道。

### 4.3 分段处理中间结构

```typescript
interface SegmentResult {
  segmentIndex: number     // 段序号 (0-based)
  content: string          // 该段 AI 输出
  tokenUsage: number       // 该段 token 消耗
}
```

## 5. 非功能需求

| 需求 | 指标 |
|------|------|
| 分段处理总耗时 | 3 段处理耗时 < 单次处理的 2 倍 |
| 质量评估耗时 | < 500ms（纯本地计算） |
| 内存占用 | 分段中间结果总内存 < 50MB |
| 向后兼容 | 短播客（< 30000 字符）零影响 |
| API 成本 | 分段处理 API 成本 < 单次处理的 1.5 倍（后续段 prompt 更短） |

## 8. 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 分段合并后内容重复 | 中 | 笔记冗余 | 合并时按实体/术语名称去重 |
| 分段边界切断完整语义 | 中 | 段间上下文丢失 | 500 字符重叠 + 按段落边界切分 |
| 质量评估误判 | 低 | 误告警 | 评分仅作参考，不阻断流程；阈值可调 |
| 外部模板文件被误删 | 低 | 回退到内置模板 | 首次启动自动导出参考模板；缺失时静默回退 |
| 分段处理 API 成本翻倍 | 低 | 用户费用增加 | 后续段 prompt 精简，仅要求补充增量内容 |
