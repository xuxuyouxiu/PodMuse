## US-001：批量输入与确认面板

**角色**：作为播客听众
**需求**：我希望一次性添加多个音频文件和 URL 到处理队列，并在确认面板中预览和调整
**价值**：以便不用逐个手动添加和等待
**优先级**：P0
**Story Points**：5

**Acceptance Criteria**：

- [ ] Given 用户拖拽 5 个 .mp3 文件到 FileDropArea, When 文件识别完成, Then 弹出批量确认面板，列出 5 个文件名及文件格式
- [ ] Given 用户在 URL 输入框粘贴 3 行 URL（每行一个）, When 解析完成, Then 确认面板显示 3 个 URL 及检测到的平台标识（小宇宙/B站等）
- [ ] Given 用户先拖入文件再粘贴 URL, When 两种方式都完成, Then 确认面板合并显示所有输入项，文件和 URL 混合排列
- [ ] Given 确认面板中已有 URL-A, When 用户再次粘贴 URL-A, Then URL-A 不重复添加，队列中对应项闪烁提示"已在队列中"
- [ ] Given 拖入的某个文件格式不支持（如 .docx）, When 文件识别完成, Then 该文件标红并提示"文件格式不支持，已自动跳过"
- [ ] Given 粘贴的某个 URL 无法识别平台, When URL 解析完成, Then 该 URL 标黄并提示"无法识别平台，将尝试直接下载"
- [ ] Given 确认面板中有多个待处理项, When 用户拖拽调整顺序, Then 项目按新顺序排列
- [ ] Given 确认面板中有多个待处理项, When 用户点击某项的删除按钮, Then 该项从列表移除
- [ ] Given 确认面板已就绪, When 用户点击"开始批量处理", Then 所有项目按顺序加入队列，确认面板关闭
- [ ] Given 已处理过的 URL 被再次添加, When 去重检查完成, Then 弹出确认"该播客已处理过，是否强制重新处理？"

**依赖**：US-002（队列引擎 IPC 接口）
**技术备注**：
- FileDropArea 组件已支持拖拽和浏览，需扩展为多文件模式
- UrlInput 组件需扩展为多行文本区域或自动识别多行粘贴
- 去重逻辑需查询 recent-task-state.ts 中的已完成任务 URL 列表
- 平台检测可复用 `platformRegistry.findAdapter(url)`

## US-002：队列引擎（串行执行与容错）

**角色**：作为播客听众
**需求**：我希望队列中的任务自动按顺序处理，某个失败后自动跳过继续下一个
**价值**：以便我可以提交队列后去做别的事，不用盯着
**优先级**：P0
**Story Points**：5

**Acceptance Criteria**：

- [ ] Given 队列中有 3 个 pending 任务, When 队列启动, Then 仅任务 1 开始处理，任务 2 和 3 保持 pending
- [ ] Given 任务 1 处理完成, When 引擎检测到完成, Then 自动启动任务 2，任务 3 保持 pending
- [ ] Given 任务 1 处理失败（如下载超时）, When 引擎捕获异常, Then 任务 1 标记为 failed 并记录失败原因，任务 2 自动开始
- [ ] Given 连续 3 个任务失败, When 第 3 个失败, Then 队列自动暂停（paused），发送提示"连续多个任务失败，已自动暂停"
- [ ] Given 任务处理中, When 任务完成, Then 该任务的临时音频文件被清理释放磁盘空间
- [ ] Given 队列最后一个任务到达终态, When 引擎检测到全部完成, Then 发送一次 Windows 系统通知"批量处理完成"
- [ ] Given 队列正在执行, When 应用主进程收到新的 podcast:process 请求, Then 拒绝并返回"队列正在执行中"

**依赖**：无（核心模块，所有其他 Story 依赖此 Story）
**技术备注**：
- 新建 `src/main/batch-queue.ts`，封装队列状态机（idle → running → paused → completed）
- 不改动 `processPodcast()` 核心函数，队列引擎在外层调用它
- 参考 `podcast-dispatcher.ts` 的 processing 锁模式，扩展为队列模型
- 新增 IPC：`batch:start`, `batch:pause`, `batch:resume`, `batch:skip`, `batch:clear`, `batch:getState`
- 新增事件：`batch:task-update`（单任务状态变化）, `batch:queue-complete`（队列完成）
- 磁盘清理：每个任务完成后调用现有的临时文件清理逻辑
- 连续失败计数在成功一个后重置

## US-003：队列控制（暂停/恢复/跳过/清空）

**角色**：作为播客听众
**需求**：我希望能暂停队列、恢复、跳过某个任务或清空整个队列
**价值**：以便灵活控制处理节奏，应对突发情况
**优先级**：P0
**Story Points**：3

**Acceptance Criteria**：

- [ ] Given 任务 2 正在处理中, When 用户点击暂停, Then 任务 2 继续完成当前步骤后暂停，后续任务不启动，按钮变为"恢复"
- [ ] Given 队列处于暂停状态, When 用户点击恢复, Then 从任务 2 暂停处继续处理，后续任务按序执行
- [ ] Given 暂停时正在执行 Whisper 转录, When 用户点击暂停, Then 按钮显示"正在暂停…"，等 Whisper 进程结束后生效
- [ ] Given 任务 3 处于 pending 状态, When 用户点击任务 3 的"跳过"按钮, Then 任务 3 标记为 skipped，下一个 pending 任务提前开始
- [ ] Given 队列中有 pending 和 processing 任务, When 用户点击"清空队列", Then 弹出确认框"确认清空？当前任务也将被取消"
- [ ] Given 用户确认清空, When 清空执行, Then 当前 processing 任务被取消，所有 pending 任务移除，队列回到 idle
- [ ] Given 某任务处于 failed 状态, When 用户点击该任务的"重试", Then 该任务重置为 pending 并加入队列末尾

**依赖**：US-002
**技术备注**：
- 暂停通过 AbortController 配合 `processPodcast` 的 signal 参数实现
- 暂停不中断正在运行的 Whisper 子进程（避免资源泄漏），而是等当前步骤完成后在步骤间隙暂停
- 跳过通过提前 abort 当前任务 + 标记 skipped 实现
- 清空 = cancel 当前 + remove 所有 pending

## US-004：队列进度展示

**角色**：作为播客听众
**需求**：我希望看到队列整体进度和每个任务的处理状态
**价值**：以便了解处理进展，判断是否需要干预
**优先级**：P0
**Story Points**：3

**Acceptance Criteria**：

- [ ] Given 队列正在执行, When 渲染器收到 batch:task-update 事件, Then 队列面板更新对应任务的状态标签（pending/processing/completed/failed/skipped）
- [ ] Given 队列有 10 个任务已完成 3 个, When 面板渲染, Then 顶部显示进度计数"3/10 已完成"
- [ ] Given 某任务正在 processing, When 面板渲染该任务行, Then 展开显示紧凑版 5 步进度指示器（复用 StepPanel 逻辑）
- [ ] Given 某任务处于 failed 状态, When 面板渲染该任务行, Then 显示红色失败原因摘要和"重试"按钮
- [ ] Given 队列有 50 个任务, When 面板渲染列表, Then 使用虚拟列表或按需渲染，保持 UI 流畅（>30fps）
- [ ] Given 队列正在执行, When 用户滚动队列列表, Then 滚动流畅无卡顿

**依赖**：US-002
**技术备注**：
- 新建 `src/renderer/components/BatchQueuePanel.tsx`
- 紧凑版 5 步进度可复用 StepPanel 的 StepInfo 数据结构，但用更精简的 UI（单行步骤条）
- 50+ 任务场景需考虑列表渲染性能，可用 react-window 或简单的 overflow-y: auto + 固定行高
- IPC 事件 `batch:task-update` 推送增量更新，避免全量刷新

## US-005：汇总报告

**角色**：作为播客听众
**需求**：我希望队列跑完后看到汇总面板，统计成功/失败/跳过数量及失败原因
**价值**：以便快速了解处理结果，针对性处理失败项
**优先级**：P1
**Story Points**：2

**Acceptance Criteria**：

- [ ] Given 队列 10 个任务全部到达终态, When 引擎触发 batch:queue-complete, Then 面板切换为汇总视图
- [ ] Given 汇总视图, When 渲染, Then 顶部显示统计卡片：总数、成功数、失败数、跳过数、总耗时
- [ ] Given 汇总视图中有失败任务, When 渲染失败区域, Then 每个失败任务显示原因摘要（如"转录超时"）和"重试"按钮
- [ ] Given 汇总视图中有成功任务, When 渲染成功区域, Then 每个成功任务显示"打开笔记"按钮
- [ ] Given 用户点击"重试全部失败", When 操作确认, Then 所有失败任务重置为 pending 并加入新队列
- [ ] Given 全部成功, When 汇总视图渲染, Then 显示"全部处理完成！"并隐藏失败区域
- [ ] Given 用户关闭汇总面板, When 面板关闭, Then 队列面板回到初始输入状态

**依赖**：US-002
**技术备注**：
- 汇总数据从队列引擎的完成事件中提取，包含每个任务的最终状态、耗时、失败原因
- "打开笔记"按钮复用现有的 `shell:openPath` IPC
- 汇总面板可内嵌在 BatchQueuePanel 中，通过队列状态切换视图

## US-006：队列持久化与恢复

**角色**：作为播客听众
**需求**：我希望关闭应用后下次打开能继续未完成的队列
**价值**：以便不用重新添加所有待处理项
**优先级**：P1
**Story Points**：3

**Acceptance Criteria**：

- [ ] Given 队列有 5 个未完成任务时应用关闭, When 应用重新启动, Then 弹出提示"上次有 N 个任务未完成，是否继续？"
- [ ] Given 用户选择"继续", When 恢复执行, Then 从第一个 pending 任务开始处理，已完成的任务保持 completed 状态
- [ ] Given 用户选择"放弃", When 操作确认, Then 清空持久化队列，不自动恢复
- [ ] Given 持久化队列中某本地文件已被移动/删除, When 恢复校验, Then 该任务标记"文件不存在"并自动跳过
- [ ] Given 每次任务状态变化时, When 状态更新, Then 队列数据写入 `batch_queue.json`（与 feishu_state.json 同目录）
- [ ] Given `batch_queue.json` 文件损坏或格式错误, When 应用启动读取, Then 忽略损坏文件，重建空队列，记录日志
- [ ] Given 上次队列全部失败, When 恢复提示, Then 显示"上次 N 个任务全部失败，是否查看？"

**依赖**：US-002
**技术备注**：
- 持久化格式：`{ tasks: BatchTask[], updatedAt: string, version: 1 }`
- 写入时机：任务状态变化时 debounce 500ms 后写入，避免频繁 IO
- 恢复校验：本地文件类型任务检查 `fs.existsSync(filePath)`，不存在则标记 skipped
- 参考 `recent-task-state.ts` 的持久化模式（同目录 JSON 文件读写）
- 应用关闭前（`window-all-closed` 或 `before-quit`）确保最后一次写入

## US-007：飞书兼容与单集回退

**角色**：作为播客听众
**需求**：我希望批量处理与现有的飞书自动监控和单集处理互不干扰
**价值**：以便新功能不影响已有工作流
**优先级**：P0
**Story Points**：2

**Acceptance Criteria**：

- [ ] Given 无批量队列在执行, When 用户粘贴单个 URL 并处理, Then 走现有单集处理流程（UrlInput → processPodcast），行为不变
- [ ] Given 无批量队列在执行, When 用户拖入单个文件, Then 走现有单集处理流程（FileDropArea → processPodcast），行为不变
- [ ] Given 批量队列正在执行, When 飞书轮询发现新 URL, Then 飞书消息进入排队等待（现有逻辑："上一个播客还在处理中，稍后轮询时处理"），不冲突
- [ ] Given 批量队列正在执行, When 用户尝试通过 URL 输入框单独添加, Then 提示"批量处理进行中，请在队列中添加"
- [ ] Given 批量队列完成, When 用户粘贴新 URL, Then 恢复为正常单集处理模式

**依赖**：US-002
**技术备注**：
- 需在全局状态中添加 `batchMode` 标志位
- `podcast-dispatcher.ts` 的 dispatch 方法需检查 batchMode，batchMode 下飞书消息不直接处理
- 单个 URL/文件的判断逻辑：输入项数量 == 1 时走旧路径，>1 时走批量路径
- StepPanel 和 ActiveTasksPanel 在 batchMode 下隐藏，由 BatchQueuePanel 接管
