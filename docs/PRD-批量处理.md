# PRD：批量处理

**版本**：v1.0
**作者**：QoderWork
**日期**：2026-06-20
**状态**：草稿

---

## 1. 背景与目标

### 1.1 背景

播客笔记助手当前每次只能处理一集播客。用户想处理一季节目（10-20 集）时，需要反复操作：粘贴 URL → 等待处理 → 粘贴下一个 → 等待……整个流程高度重复，且人必须全程盯着。飞书自动轮询虽然能部分缓解这个问题，但仅限飞书场景，手动使用时体验很差。批量处理让用户一次性提交所有待处理内容，然后去忙别的事。

### 1.2 目标用户

| 用户角色 | 特征描述 | 核心诉求 | 使用场景 |
|---------|---------|---------|---------|
| 播客重度听众 | 每周听 5+ 集播客，积累了大量未处理的音频/URL | 一次性处理积压内容，不逐条手动操作 | 周末集中处理一周攒下的播客 |
| 内容整理者 | 系统性地将播客转化为知识库，追求覆盖率 | 批量补全历史节目笔记 | 新发现一个播客，想把全部历史节目都做笔记 |
| 飞书协作场景用户 | 已开启飞书监控，偶尔也手动添加 | 手动和自动混合使用，不冲突 | 飞书没覆盖的本地录音也需要处理 |

### 1.3 业务目标与成功指标

| 目标 | 衡量指标 | 目标值 | 监测方式 |
|------|---------|--------|---------|
| 减少用户操作次数 | 处理 N 集所需的点击次数 | 从 N×3 次降至 ≤5 次 | 手动测试验证 |
| 支持无人值守 | 队列中途失败率（非内容原因） | < 5% | 汇总报告中统计 |
| 提升处理效率 | 用户从提交到全部完成的等待中无需人工干预的比例 | > 90% | 用户反馈 |

## 2. 需求概述

支持一次性添加多个音频文件和/或 URL 形成处理队列，应用自动串行执行、独立显示进度、容错继续，完成后输出汇总报告。

## 3. 功能详细设计

### 3.1 批量输入（添加任务到队列）

**功能描述**：用户通过拖拽文件、文件浏览、粘贴 URL 等方式，一次性添加多个待处理项到队列中。

**用户故事**：作为播客听众，我希望一次性把多个音频文件和 URL 加入处理队列，以便不用逐个手动添加。

**优先级**：P0

**业务规则**：
1. 支持的输入方式：拖拽多个文件、文件浏览器多选、粘贴多行 URL（每行一个）、三种方式混合使用
2. 支持的本地文件格式：.mp4, .mov, .avi, .wmv, .mp3, .wav, .aac, .flac（与现有 FileDropArea 一致）
3. 支持的 URL 格式：小宇宙、B站、YouTube、喜马拉雅、Apple Podcasts、直链音频（与现有 UrlInput 一致）
4. 去重规则：同一 URL 不重复添加（本地文件按路径去重）；若 URL 已在已完成任务中，提示"已处理过，是否强制重新处理"
5. 队列添加顺序：按用户添加的先后顺序排列，支持拖拽调整顺序
6. 混合队列：本地文件和 URL 可以在同一队列中共存

**交互流程**：
1. 用户在输入区域操作：拖拽多个文件到 FileDropArea、点击"浏览文件"多选、在 URL 输入框粘贴多行 URL
2. 系统识别出多个输入项后，弹出批量确认面板，显示待处理列表（文件名/URL + 检测到的平台标识）
3. 用户可在此面板中调整顺序（拖拽排序）、移除个别项（点删除按钮）、或清空重来
4. 用户点击"开始批量处理"，所有项目加入队列

**异常处理**：

| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 文件格式不支持 | 该文件标红，不加入队列 | "以下文件格式不支持：xxx，已自动跳过" |
| URL 无法识别平台 | 该 URL 标黄，仍加入队列（尝试直链处理） | "以下链接无法识别平台，将尝试直接下载" |
| 文件已存在于队列中 | 忽略重复添加 | 队列中对应项闪烁提示"已在队列中" |
| 文件已处理过 | 弹出确认对话框 | "该播客已处理过，是否强制重新处理？" |
| 拖入空文件夹 | 忽略，不添加任何项 | 无提示 |

### 3.2 队列管理（暂停/恢复/取消/调整）

**功能描述**：用户对正在执行的队列进行暂停、恢复、取消单个任务或清空整个队列的操作。

**用户故事**：作为用户，我希望能随时暂停队列或取消某个任务，以便灵活控制处理节奏。

**优先级**：P0

**业务规则**：
1. 队列状态：空闲（idle）→ 运行中（running）→ 已暂停（paused）→ 运行中/已完成（completed）
2. 暂停：暂停当前正在处理的任务（等当前步骤完成后暂停，不中断 Whisper 进程），后续任务等待
3. 恢复：从暂停状态继续，先完成当前任务剩余步骤，再处理后续任务
4. 取消单个任务：跳过当前任务，标记为"已跳过"，继续处理下一个
5. 清空队列：取消所有未开始的任务，当前正在执行的任务等其完成或手动取消
6. 调整顺序：仅未开始（pending）的任务可以拖拽调整顺序，正在执行的任务不可移动
7. 队列中每个任务有三种状态：等待中（pending）、处理中（processing）、已完成（completed）、已失败（failed）、已跳过（skipped）

**交互流程**：
1. 队列面板显示在输入区域下方，列出所有任务及其状态
2. 顶部操作栏：暂停/恢复按钮、清空按钮、完成计数（如 "3/10 已完成"）
3. 每个任务行显示：序号、文件名/URL 缩略、平台图标、状态标签、操作按钮（跳过/删除）
4. 正在处理的任务展开显示 5 步进度（复用 StepPanel 的紧凑版）

**异常处理**：

| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 暂停时正在执行 Whisper | 等 Whisper 当前 chunk 结束后暂停 | 暂停按钮变为"正在暂停…" |
| 清空队列时正在处理中 | 先取消当前任务再清空 | "确认清空队列？当前正在处理的任务也将被取消" |
| 应用关闭时队列未完成 | 队列持久化到磁盘，下次启动提示继续 | 启动时弹出"上次有 N 个任务未完成，是否继续？" |

### 3.3 串行执行与容错

**功能描述**：队列中的任务严格按顺序逐个执行，单个任务失败不阻塞后续任务。

**用户故事**：作为用户，我希望某个播客处理失败后，队列能自动跳过继续处理后面的，不用我手动干预。

**优先级**：P0

**业务规则**：
1. 严格串行：同一时刻只有一个任务在执行，前一个完成后自动启动下一个
2. 失败隔离：单个任务的任何步骤失败（下载失败、转录失败、AI 超时等），该任务标记为"已失败"并记录失败原因，队列自动继续下一个
3. 飞书通知兼容：每个任务完成/失败时照常触发飞书消息推送（如果飞书监控已开启）
4. 系统通知：仅在整个队列全部完成时发送一次 Windows 通知（而非每个任务都通知）
5. 资源释放：每个任务完成后释放临时文件（音频缓存），避免磁盘占满（可配置保留缓存）

**交互流程**：
1. 队列自动按顺序执行，无需用户干预
2. 失败的任务行展开显示失败原因（红色文字）和"重试"按钮
3. 用户可以点击"重试"让失败任务重新加入队列末尾

**异常处理**：

| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 连续 3 个任务失败 | 暂停队列，提示用户检查配置 | "连续多个任务失败，已自动暂停。请检查网络或配置后恢复" |
| 磁盘空间不足 | 暂停队列 | "磁盘空间不足，请清理后恢复" |
| AI API 余额不足 | 暂停队列 | "AI 服务余额不足，请充值后恢复" |
| 网络断开 | 当前任务标记失败，后续任务也预判会失败，自动暂停 | "网络连接已断开，队列已暂停" |

### 3.4 队列持久化

**功能描述**：队列状态写入磁盘，应用关闭后重新打开可以恢复未完成的队列。

**用户故事**：作为用户，我希望关闭应用后下次打开能继续上次没处理完的队列，不用重新添加。

**优先级**：P1

**业务规则**：
1. 持久化内容：队列中每个任务的路径/URL、类型（本地/URL）、状态、添加时间、失败原因
2. 持久化时机：每次任务状态变化时写入（新增、开始、完成、失败、跳过）
3. 恢复逻辑：应用启动时检测未完成的队列，弹出提示"上次有 N 个任务未完成，是否继续？"
4. 用户选择继续：从第一个 pending 任务开始恢复执行（不重试已失败的，除非用户手动点重试）
5. 用户选择放弃：清空持久化队列，不自动恢复
6. 存储位置：与 feishu_state.json 同目录，文件名 `batch_queue.json`

**异常处理**：

| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 本地文件已被移动/删除 | 该任务标记为"文件不存在"，跳过 | 队列中该项标红显示"源文件已丢失" |
| 持久化文件损坏 | 忽略并重建空队列 | 日志记录，不弹窗打扰 |
| 上次队列全部失败 | 正常提示恢复 | "上次 N 个任务全部失败，是否查看？" |

### 3.5 汇总报告

**功能描述**：整个队列处理完成后，展示一个汇总面板，统计成功/失败/跳过的数量及详情。

**用户故事**：作为用户，我希望队列跑完后能快速看到哪些成功、哪些失败及原因，以便针对性处理。

**优先级**：P1

**业务规则**：
1. 触发时机：队列中所有任务都到达终态（completed/failed/skipped）时自动弹出
2. 报告内容：总数、成功数、失败数、跳过数、总耗时、每集平均耗时
3. 失败详情：每个失败任务的原因摘要（如"转录超时"、"AI 返回错误"）
4. 可操作项：失败任务旁有"重试"按钮，成功后有"打开笔记"按钮
5. 报告可关闭，关闭后队列面板回到初始状态

**交互流程**：
1. 最后一个任务完成后，队列面板平滑切换为汇总视图
2. 顶部显示统计卡片（成功/失败/跳过/总耗时）
3. 下方列表显示每个任务的最终状态
4. 用户可点击"重试全部失败"一键将所有失败任务重新加入新队列

**异常处理**：

| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 全部成功 | 正常显示，隐藏失败区域 | "全部处理完成！" + 庆祝动画 |
| 全部失败 | 显示所有失败原因，建议检查配置 | "全部处理失败，请检查网络或 Whisper 配置" |

## 4. 非功能需求

| 类别 | 要求 | 验收标准 |
|------|------|---------|
| 性能 | 队列状态更新不阻塞主线程 | UI 帧率 > 30fps，即使在 Whisper 处理期间 |
| 稳定性 | 单个任务崩溃不影响进程 | 任何任务异常不导致应用崩溃 |
| 磁盘 | 大批量处理时控制临时文件占用 | 每完成一个任务释放其临时文件，峰值占用 ≤ 2 个任务的临时文件大小 |
| 内存 | 长队列（50+ 项）不导致内存泄漏 | 内存增长 < 50MB（50 项队列） |
| 兼容性 | 与现有单集处理流程兼容 | 单集处理的 URL 输入和文件拖拽仍正常工作 |

## 5. 数据需求

| 事件名 | 触发条件 | 关键属性 | 用途 |
|--------|---------|---------|------|
| batch_queue_created | 用户创建批量队列 | queue_size, input_types (file/url/mixed) | 了解批量使用频率和输入偏好 |
| batch_task_completed | 单个任务完成 | task_index, duration_seconds, success | 统计单任务平均耗时 |
| batch_queue_finished | 整个队列完成 | total, succeeded, failed, skipped, total_duration | 评估批量处理效果 |
| batch_queue_resumed | 用户恢复持久化队列 | remaining_count | 了解持久化使用率 |

| AC-02 | 批量添加 URL | 用户有 3 个小宇宙链接 | 粘贴 3 行 URL 到输入框 | 识别出 3 个 URL，显示平台标识 |
| AC-03 | 混合输入 | 队列中有文件和 URL | 点击开始批量处理 | 所有项目按顺序加入队列 |

| AC-05 | 串行执行 | 队列有 3 个任务 | 开始处理 | 任务 1 完成前，任务 2 不开始 |
| AC-06 | 失败继续 | 任务 1 处理失败 | 自动处理 | 任务 1 标记失败，任务 2 自动开始 |
| AC-07 | 暂停 | 任务 2 正在处理 | 点击暂停 | 任务 2 暂停，后续任务等待 |
| AC-08 | 恢复 | 队列处于暂停状态 | 点击恢复 | 从任务 2 暂停处继续 |

| AC-10 | 连续失败暂停 | 连续 3 个任务失败 | 自动处理 | 队列自动暂停，提示用户检查 |
| AC-11 | 汇总报告 | 队列 10 个任务全部到达终态 | 自动触发 | 显示汇总：成功/失败/跳过数量和详情 |
| AC-12 | 持久化恢复 | 队列有 5 个未完成任务时关闭应用 | 重新启动应用 | 弹出恢复提示 |
| AC-13 | 持久化继续 | 用户选择继续 | 确认恢复 | 从第一个 pending 任务开始执行 |
| AC-14 | 文件丢失处理 | 持久化队列中某本地文件已被删除 | 恢复队列 | 该任务标记"文件不存在"并跳过 |
| AC-15 | 重试失败 | 汇总报告中有 2 个失败任务 | 点击"重试全部失败" | 2 个失败任务加入新队列 |
| AC-16 | 磁盘清理 | 任务 1 完成 | 自动处理 | 任务 1 的临时音频文件被释放 |
| AC-17 | 单集兼容 | 无批量队列 | 粘贴单个 URL 处理 | 与现有单集处理流程完全一致 |

## 7. 排期建议

| 阶段 | 预估工时 | 依赖 | 风险点 |
|------|---------|------|--------|
| 队列引擎（主进程） | 3 天 | 无 | 需重构 PodcastDispatchService 的 processing 锁为队列模型 |
| 队列持久化 | 1 天 | 队列引擎 | 文件写入时机和并发安全 |
| 批量输入 UI | 2 天 | 无 | 多文件拖拽和 URL 解析的边界情况 |
| 队列面板 UI | 2 天 | 队列引擎 IPC | 大量任务时的列表渲染性能 |
| 汇总报告 UI | 1 天 | 队列引擎 | 无 |
| 联调与集成 | 1 天 | 全部 | 与飞书监控、任务恢复系统的兼容 |
| 测试 | 2 天 | 全部 | 大批量场景测试（20+ 任务） |
| **合计** | **~12 天** | | |

## 8. 风险与依赖

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 现有单任务架构重构成本高 | 中 | 高 | 队列引擎封装为独立模块，不改动 processPodcast 核心函数 |
| 大批量处理时 Whisper 进程资源泄漏 | 中 | 高 | 每个任务结束后强制检查和清理子进程 |
| 长时间运行后应用被系统休眠 | 低 | 中 | 处理期间禁用系统休眠（Electron powerSaveBlocker） |
| 磁盘空间被大量临时文件占满 | 低 | 中 | 逐任务清理策略，队列开始前预估磁盘需求 |
| 持久化队列与实际文件系统状态不一致 | 中 | 低 | 恢复时校验每个文件是否存在，不存在则标记跳过 |
